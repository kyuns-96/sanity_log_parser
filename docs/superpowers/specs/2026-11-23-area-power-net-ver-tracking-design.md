# 프로젝트 비교 2단계 — NET_VER별 자동 추적과 결과 메일

2026-11-23 · 합의한 제품 동작 · 구현 대기

프로젝트 관리자는 비교 기준을 한 번 정하고, 블록 담당자는 평소처럼 CSV를 올린다. 필수 corner마다 검증된 데이터가 들어오면 서버가 분석한다. 블록 담당자는 자기 블록의 결과를 받고, 프로젝트 관리자와 TOP 관계자는 해당 NET_VER의 Full-chip과 모든 대상 블록을 한 통에서 본다.

현재 제공하는 기능은 수동 비교, instance 매핑 승인, AI 분석 요청, 요약 메일 요청이다. 이 문서는 다음 단계의 화면과 실행 규칙을 정의한다. [현재 제품 사용법](../../../area_power/README.md) · [1단계 AI 분석 설계](2026-11-17-area-power-ai-triage-design.md)

## 1. 프로젝트 비교를 열면 보이는 것

| 화면 | 사용자가 확인하거나 변경하는 내용 |
| --- | --- |
| **NET_VER 현황** · 첫 화면 | 상단에서 선택한 프로젝트를 이어받는다. NET_VER별 실제 도착일·마감일, Full-chip과 하위 블록의 도착·분석 건수, 블록별 미도착 corner·매핑 확인·분석 실패 사유, TOP 메일 상태를 표시한다. 블록이나 대기 사유를 누르면 해당 결과 또는 설정으로 이동한다. |
| **추적 설정** | 현재·기준 프로젝트와 블록을 연결하고 필수 corner, 승인된 기준 실행, 매핑, Design info, 예상 변화, 전력 목표 및 수신자를 지정한다. 활성화 전에는 기존 실행으로 분석 대상과 메일 내용을 미리 볼 수 있다. |
| **블록 결과** | NET_VER·블록·corner·비교 기준을 선택한 상태로 기존 hierarchy 표를 연다. 이상 항목을 누르면 해당 instance와 판단 근거를 보여준다. 메일의 결과 링크도 발송 당시 실행을 연다. 임의의 두 실행을 살펴보는 **수동 비교**를 계속 제공한다. |

예를 들어 **NET_023 · 마감 12/08 · Full-chip 도착 1/1 · 하위 블록 도착 1/2 · TOP 메일 대기**를 열면 다음 세 행이 보인다.

| 대상 | 필수 corner 도착 | 분석 완료 | 현재 상태와 동작 |
| --- | --- | --- | --- |
| P2 · Full-chip | 1/1 | 1/1 | 대표 전력 88 mW · 목표 3 mW 초과 → Full-chip 결과 보기 |
| CPU | 1/1 | 0/1 | TT 분석 중 → 진행 상황 보기 |
| GPU | 1/2 | 1/2 | SS 미도착 → 도착한 TT 결과 보기 |

## 2. 다음 업로드에 적용할 설정

| 적용 범위 | 저장할 내용과 재사용 규칙 |
| --- | --- |
| 프로젝트 | 기존 지정 기준 프로젝트, 기본 필수 corner 목록, 마감 기간(기본 7일, 프로젝트별 변경 가능), 관리자·TOP 배포 목록을 설정한다. 프로젝트 생성 시 등록한 공정과 NAND2_D1 Unit area를 사용한다. |
| 프로젝트 × NET_VER | **실제 netlist 도착일**과 대상 블록 목록을 등록한다. 도착일에 마감 기간을 더해 마감일을 정한다. 첫 CSV가 늦어도 같은 마감일을 쓴다. 프로젝트·블록의 수신자와 추적 설정은 다음 NET_VER에 이어받고, 각 회차에 적용한 대상·조건을 기록한다. |
| 블록 | 현재 블록과 기준 블록, 설계 단계(PRE/POST 등), 필수 corner 한 개 이상, 블록 담당자 개인 주소를 설정한다. 프로젝트 기본 corner를 상속하거나 블록별로 바꾼다. CPU는 TT만, GPU는 TT와 SS 모두를 요구할 수 있다. 추가 corner는 조회 가능하며 필수 수량 계산에서 제외한다. |
| 블록 × corner | 기준 블록의 **승인된 실행**을 고정한다. 기준 쪽에 새 CSV가 생겨도 기존 기준을 유지하고, 담당자가 기준을 교체하면 다음 분석부터 적용한다. 같은 프로젝트의 이전 버전을 기준으로 쓸 때는 같은 블록의 명시적 버전 계보에서 실행을 선택한다. |
| 블록·instance × 적용 NET_VER | 블록의 기준 설계 대비 변경사항과 주요 instance 목록을 유지하고, 버전별 변경 메모·예상 범위·목표의 적용 시작점을 기록한다. 메모를 입력하지 않은 상태와 담당자가 확인한 ‘변경 없음’을 구분한다. |

**Full-chip은 별도 업로드다.** 같은 프로젝트 안에서 등록된 블록명과 프로젝트명이 같으면 그 블록을 Full-chip TOP으로 인식한다. 현재 프로젝트 `P2`와 기준 프로젝트 `P1`의 Full-chip 비교 쌍은 `P2/P2`와 `P1/P1`이다. 이 이름 규칙은 이미 소속이 확인된 블록의 역할을 정하는 데 사용한다. 현황의 Full-chip과 하위 블록 수는 따로 센다.

CSV가 없어도 블록 간 연결을 먼저 저장한다. 양쪽 데이터가 갖춰지면 승인된 매핑을 적용 버전과 실제 경로에 대조한다. 유효한 명시 규칙이 우선하며, 기존 상대 경로 대응 규칙도 사용한다. 이름 변경·분할·병합이 모호하면 해당 블록을 **매핑 확인 필요**로 표시하고 AI 제안과 경로 검토 화면으로 연결한다. 승인 후에는 이미 도착한 실행으로 분석을 이어간다. 다른 블록은 독립적으로 진행한다.

## 3. 업로드, 수정본, 분석 상태

1. **활성화**할 때 추적을 맡은 사용자, 현재 프로젝트 쓰기 권한과 VWP의 프로젝트 비교 AI 설정을 확인한다. 업로드는 수신 계기로 사용하고, AI 실행에는 추적 담당자의 권한과 인증을 적용한다. 수신자 주소와 프로젝트 조회·수정 권한은 각각 관리한다.
2. **검증 성공**한 필수 corner의 현재 CSV와 승인한 기준 실행이 준비되면, 다른 corner를 기다리지 않고 그 쌍을 분석한다. 현재 CSV가 먼저 와도 기준 실행 승인이나 매핑 확인이 끝나면 같은 파일로 이어간다. 비교에 사용한 양쪽 실행, 매핑 revision, 조건, 예상 범위·목표와 메모 revision을 결과에 고정한다. 현황에는 블록별로 어느 REVISION을 집계했는지 표시한다.
3. **수정 업로드**는 같은 프로젝트·NET_VER·블록·REVISION·설계 단계·분석 조건 안에서 현재 쪽 최신 검증본을 교체하고 재분석한다. 검증 실패는 직전 정상본을 유지하며 실패 사유를 표시한다. 이전 실행이 뒤늦게 끝나도 더 최신 수정본의 상태를 덮어쓸 수 없다. 다른 corner나 REVISION은 별도 실행으로 취급한다.
4. **블록 분석 완료**는 해당 블록의 필수 corner가 모두 도착하고 각 최신 검증본의 분석이 끝난 시점이다. 예를 들어 GPU의 TT가 먼저 오면 TT 결과를 보여주면서 ‘SS 미도착’을 표시한다. 정상적으로 분석한 결과에 ‘확인 필요’ instance가 있어도 결과를 전달한다. 인증 만료·AI 실패·분석 중단은 별도 상태로 표시한다.

## 4. 무엇을 이상으로 볼 것인가

2단계 자동 후보 선별의 기본 지표는 **Logic Area(`logic_area`)와 Total Power(`pwr_all_total_mw`)**다. 현재 1단계 엔진은 Total Area로 증가 후보를 찾는다. 2단계에서는 면적의 증감률과 최소 면적 조건 모두에 Logic Area를 사용한다. 주요 instance는 변화가 작아도 분석한다. 비교 표의 Area ↔ Gate Count 스위치를 바꿔도 자동 판정은 같은 Logic Area 기준을 사용한다. [현재 후보 선별 코드](../../../area_power/common/triage.py)

**Typical 조건과 목표 전력(mW)은 독립적으로 버전 관리한다.** 프로젝트가 대표로 쓰는 실제 corner와 mode·클록·activity 등 분석 조건을 지정한다. 대표 조건 또는 목표가 바뀌면 적용 시작 NET_VER를 기록한다.

| 전력 비교 | 예시 | 결과 해석 |
| --- | --- | --- |
| 각 프로젝트의 Typical | 기준 100 mW @ 0.80 V → 현재 90 mW @ 0.70 V | 대표 전력 −10%. 전압 변경을 함께 표시하고 대표 조건 결과에 적용되는 승인 예상과 현재 목표를 평가한다. |
| 동일 조건 | 기준 100 mW @ 0.80 V → 현재 110 mW @ 0.80 V | 나머지 분석 조건도 일치하면 +10%를 instance별 설계 변화 분석에 사용한다. |

동일 조건은 실제 공정 corner·전압·온도·PEX와 mode·클록·activity 등 업로드의 분석 조건으로 확인한다. 조건이 비어 있으면 ‘조건 미확인’, 대응 실행이 없으면 ‘동일 조건 데이터 없음’으로 표시한다. Typical 조건이 다르면 대표 전력 차이에 변경 조건을 병기하고, instance별 전력 변화의 원인은 별도의 동일 조건 쌍에서 분석한다. 선택 사항인 동일 조건 실행은 조기 발송의 완료 조건에서 제외한다. 전체 Typical Power와 전체 목표 달성 여부에는 **Full-chip 리포트 루트의 대표 corner Total Power**를 사용한다. 블록 누적값과 여러 corner의 전력은 각각 표시한다.

**예상 변화와 목표 달성 여부도 별도로 판정한다.** AI가 Design info에서 대상 경로·지표·비교 조건·적용 NET_VER·예상 증가 또는 감소 범위를 제안하고 담당자가 한 번 확인한다. 이후 업로드에서는 코드가 승인 범위를 대조한다. 범위 안의 변화는 ‘설명됨’ 건수와 근거를 남기고 이상 상세 목록에서 생략한다. 방향만 있는 메모는 ‘방향 일치’까지만 설명할 수 있다. 예상 범위는 승인한 대상·지표에만 적용하며 다른 지표, 다른 instance, 목표 미달은 독립적으로 확인한다.

예를 들어 기준 Typical 100 mW에서 10–20% 감소를 예상하고 새 목표가 **85 mW 이하**라면 82 mW는 ‘설명됨·목표 달성’, 88 mW는 ‘설명됨·목표 3 mW 초과’, 97 mW는 ‘예상 절감 미달·목표 12 mW 초과’다. 반대로 `GPU/u_cache`의 Logic Area가 용량 확장으로 15–25% 증가할 예정이면 +20%는 설명되고 +45%는 검토 대상이다. Full-chip 합계가 예상에 들어와도 블록별 판단은 수행한다.

## 5. 누구에게 언제 보낼 것인가

| 수신자 | 발송 조건 | 메일 내용 |
| --- | --- | --- |
| 블록 담당자 | 자기 블록의 필수 corner 분석이 모두 끝나면 발송. 이후 유효한 수정본의 분석이 완료되면 해당 블록 담당자에게 수정 결과 발송 | 자기 블록의 corner별 결과를 한 통에 담는다. Logic Area·Total Power, 설명된 변화 건수, 목표 미달·예상 밖 변화·확인 필요 instance와 결과 링크를 포함한다. |
| 프로젝트 관리자·TOP 관계자 | **Full-chip과 모든 대상 블록의 분석 완료 시점과 마감 중 빠른 시점**에 프로젝트·NET_VER당 요약 한 통 | Full-chip 대표 전력·목표 대비 차이, 대상 블록 전체의 도착·분석 건수를 먼저 표시한다. 이어 모든 블록을 한 줄씩 표시하고, 주의가 필요한 블록을 먼저 배치한다. |

12월 1일 netlist 도착, 기간 7일이면 마감일은 12월 8일이다. 5일에 마지막 필수 CSV 분석이 끝나면 그날 TOP 요약을 보낸다. 8일 마감에 GPU의 SS가 아직 없거나 매핑 확인·분석 진행·실패가 남았다면 그 상태를 담아 발송한다. Full-chip도 미도착이면 ‘Full-chip 미도착 · 전체 목표 판정 대기’로 표시한다.

TOP 요약에 넣을 결과는 발송 요청 시점에 고정한다. 그 전까지 완료된 수정은 요약에 반영하고, 새 수정본이 분석 중이면 진행 상태를 표시한다. 발송 후에 도착한 파일이나 수정본은 블록 담당자와 최신 현황에 반영하며 ‘발송 후 수정’을 표시한다. 메일 링크에서는 당시 결과와 최신 결과를 식별할 수 있다.

## 6. 서버 처리와 구현 시 확인 기준

브라우저를 닫아도 검증 완료·분석 완료·마감 처리가 이어져야 한다. 중앙 VWP가 AI를 실행하고 OA가 사내 메일 요청을 담당한다. 기존 압축 CSV와 비교 참조를 재사용하며 회차별로 전체 hierarchy 수치 행을 복제하지 않는다. 메일 요청과 사내 서비스 접수·일부 거부·결과 불명은 구분해 현황에 남긴다. [사내 메일 연동 계약](../../../oa/MAIL_INTEGRATION.md)

| 확인할 상황 | 기대 동작 |
| --- | --- |
| 같은 업로드 완료 이벤트를 재처리하거나 서버가 재시작됨 | 같은 입력과 설정으로 진행 중이거나 끝난 작업을 찾아 이어간다. 동일한 블록 결과의 메일 요청은 하나다. |
| 마지막 분석 완료와 마감 처리가 동시에 실행됨 | 프로젝트·NET_VER의 TOP 발송 요청을 한 번만 확정한다. 이미 요청한 외부 발송의 접수 여부가 불명확하면 ‘결과 불명’으로 남기고 재전송 전 접수 내역을 확인한다. |
| 기준 교체, 수정본 재분석 또는 Design info 수정 | 다음 분석에는 새로 적용할 입력을 사용하고 이전 결과·발송본은 당시 입력으로 조회한다. |
| 담당자 권한·VWP 인증·사내 메일 연결 문제 | 숫자 결과, AI 판정 상태, 메일 접수 상태를 각각 보존하고 현황에서 막힌 단계를 식별할 수 있다. |

구현 시 확정할 운영 값은 **마감일의 시각과 시간대**다. 화면은 날짜와 함께 실제 발송 마감 시각을 표시한다. 사내 모델의 판단 품질과 회사 메일의 실제 접수는 사내 환경에서 확인한다.
