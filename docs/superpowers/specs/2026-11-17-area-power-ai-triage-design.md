# Area/Power AI 이상치 분석 설계 (instance 단위 진단)

2026-11-17 · 설계 담당 작성 · 상태: 사용자 승인(2026-11-17, "그대로 진행"). 독립 검토 1회 반영

표시: **[사용자]** 는 사용자가 대화에서 정한 것, **[제안]** 은 설계 담당이 채운 것으로 사용자가 고칠 수 있다.

## 1. 의도

사람이 미리 적어 둔 메모(NET_VER별 업데이트 사항, 프로젝트가 바뀔 때의 Block 변경 사항)와 instance mapping을 근거로, 비교 결과에서 **설명되지 않는 이상치를 가진 instance를 AI가 골라 사용자에게 메일로 알린다.** [사용자]

지금은 사람이 비교 표를 직접 훑는다. 보는 순서는 다음과 같다. [사용자]

1. Area 증가량이 과도한지 본다. 이유 없이 늘었으면 의심한다.
2. Power가 가장 중요하다. Area는 비슷한데 Power가 많이 늘었으면 Vth 구성을 본다.
3. Vth 구성에 이상이 없으면 driving strength 구성을 본다.

NET_VER가 바뀌었다는 것은 RTL이 바뀌었다는 뜻이므로, 같은 프로젝트의 이전 NET_VER 대비 갑작스러운 변화도 검토 대상이다. [사용자]

## 2. 목표 · 비목표 · 하면 안 되는 것

**목표 (1단계)**

- 비교 화면의 **"AI 분석" 버튼**으로 실행한다. 초반에는 noise가 많을 것이므로 자동 실행하지 않는다. [사용자]
- 분석 대상 비교는 두 가지다: 기준 프로젝트와의 비교, **같은 프로젝트의 이전 NET_VER(버전)와의 비교.** [사용자]
- 사용자가 등록한 **주요 instance는 변화 크기와 무관하게 반드시 분석한다.** [사용자]
- 결과를 화면에서 먼저 확인하고, 사용자가 "메일 보내기"를 눌러야 요약 메일 한 통이 나간다. [제안]
- 분석 엔진은 버튼과 분리한다. 입력은 (비교, 기준 숫자, 적용 메모, 주요 instance, 수신자, 요청자의 AI 연결)뿐이어서, 나중에 "업로드되면 실행"이라는 시작 조건과 사전 등록만 붙이면 자동화된다. [제안]

**비목표 (1단계에서 만들지 않음)**

- CSV 업로드 시 자동 분석·자동 메일 (나중 단계). [사용자]
- 감소 방향의 이상치 선별 (주요 instance는 감소도 그대로 보고). [제안]
- 메모에 적힌 수치 범위("20~30%")를 코드가 직접 대조하는 기능. 1단계에서는 AI가 판단한다. [제안]
- instance별 알림 레코드(읽음·확인·해소)와 건별 메일. 기존 엔진의 해당 기능은 건드리지 않고 사용하지도 않는다. [제안]
- 사람의 오탐 표시를 다음 분석에 학습시키는 기능. [제안]

**하면 안 되는 것**

- AI가 수치·대응·비교 가능성을 바꾸는 것. 수치는 전부 코드가 계산한다.
- 일부만 분석하고 전체를 분석한 것처럼 표시하는 것.
- AI 미설정·실패·잘못된 응답을 성공이나 "설명됨"으로 바꾸는 것. 해당 instance는 `확인 필요`로 남긴다.
- 메모가 없다는 이유로 "설명됨" 처리하는 것.
- 메모 안의 문장을 지시로 따르는 것. 메모는 데이터다.
- 검토 없이 메일이 나가는 것(1단계).

## 3. 제약

- **DB:** 기존 두 테이블만 쓴다. 새 테이블·DDL 없음. `job_kind`는 CHECK 제약으로 `ingest/compare/extract/judge/mail`만 허용되므로 **새 job kind를 만들 수 없다.** AI 작업은 `judge`, 메일은 `mail`을 쓰고 부모 레코드의 내용으로 분기한다.
- **실행 위치:** OA는 요청 등록·조회만 한다. AI 호출은 지금처럼 **중앙 VWP 프로세스**가 DB 작업 큐에서 가져가 실행한다. 브라우저·OA가 모델을 직접 호출하지 않는다.
- **AI 신원:** 로그인한 SSO 사용자의 기존 로그 AI 연결(`REVIEW` 작업 선택)을 요청 시점에 고정한다. 익명 업로드는 AI를 실행할 수 없다. 실행 중 요청자의 쓰기 권한·연결 설정·credential이 바뀌면 중단한다(기존 `area_power/common/ai.py`의 `Runtime` 동작).
- **메일:** `MailSender` Protocol만 호출한다. 사내 어댑터(`oa/integration/corporate_mail.py`)는 OA 담당이 구현해야 실제 발송된다. 미연결이면 발송 실패로 남는다.
- **OA와 중앙 VWP는 같은 release**여야 한다(`area_power/common` 공유).
- **검증 규칙(AGENTS.md):** 사용자 승인 없이 새 테스트·fixture·mock·검증 스크립트 파일을 추가하지 않는다. 데스크톱 1920×1080·5120×2160만 확인한다. 외부 개발 환경에서는 사내 모델을 호출할 수 없으므로 **AI 판단 품질은 사내에서만 확인 가능**하다.
- 데모(메모리) 모드는 AI 호출을 흉내 내지 않는다(`model_called=false`, `확인 필요`).

## 4. 검토한 방법

| | A. 기존 엔진 그대로 | **B. instance 단위 진단 (선택)** | C. 한 번에 통째로 |
|---|---|---|---|
| 방식 | 메모에서 예상 범위 추출 → 튄 지표마다 AI 1회 | 코드가 후보·진단 자료 작성 → AI가 20개씩 묶어 판정 | 상위 변화 200개와 메모를 1회 호출 |
| AI 호출 수 (후보 K) | K × 지표 수 | K ÷ 20 | 1 |
| Power→Vth→Drive 순서 반영 | 불가 | 가능 | AI 재량 |
| 모든 후보 판정 보장 | 있음 | 있음 | 없음 |
| 메일 | 건당 1통 | 요약 1통 | 요약 1통 |

사용자가 **B**를 골랐다. 평소 검토 방식(instance 단위, Power→Vth→Drive)과 같은 모양이고, 조상 묶기와 묶음 판정으로 noise와 호출 수를 같이 줄이며, 모든 후보가 판정되므로 자동화로 넘어가기 쉽다. A는 instance 하나가 지표별로 쪼개지고 진단 흐름을 담지 못한다. C는 상위 N 밖을 보지 않고 결과가 흔들린다. AI 없이 규칙만 쓰는 방법은 자연어 메모를 읽지 못해 제외했다.

기존 엔진(`area_power/vwp_server/ai.py`의 추출·지표별 판정·알림)은 삭제하지 않고 그대로 둔다. 새 엔진은 별도 모듈로 추가한다.

## 5. 동작

### 5.1 사람이 미리 넣는 것

| 입력 | 범위 | 형식 | 저장 |
|---|---|---|---|
| **NET_VER 업데이트 메모** | 프로젝트 · Block · NET_VER | 자유 글 | 기존 `change` 레코드 재사용, payload에 `note_kind='net_ver'`, `net_ver` 추가 |
| **프로젝트 변경 메모** | 현재 프로젝트 · Block · 기준 프로젝트 | 자유 글 | `change` 레코드, `note_kind='project_change'`, `baseline_project_id` |
| **주요 instance** | 프로젝트 · Block | 현재 쪽 instance 경로 목록 (검색 선택 또는 붙여넣기) | 기존 `target` 레코드 재사용 (scope=node) |
| **공정** | 프로젝트 | 짧은 글 (공정 이름) | Area `project` 레코드 payload의 `process`. 기준 설정과 같은 방식으로 row_version 충돌을 검사 |
| instance mapping | 지금과 같음 (규칙·CSV, 루트 기준 상대 경로 자동 대응) | — | 변경 없음 |

메모와 주요 instance를 고치면 새 revision이 된다. 이미 끝난 분석은 당시 내용을 그대로 보관한다. [제안]

### 5.2 어떤 메모가 적용되는가 (코드가 결정, AI가 정하지 않음)

- **버전 비교:** 기준 버전에서 현재 버전까지의 명시적 계보(`previous_version_id`)에서, 기준 NET_VER **다음부터** 현재 NET_VER까지의 NET_VER 메모. 같은 NET_VER 안의 REVISION 비교면 NET_VER 메모는 없고, AI에 "RTL 동일"이라고 알린다.
- **프로젝트 비교:** (현재 프로젝트·Block, 기준 프로젝트)의 프로젝트 변경 메모 + 현재 버전 계보 전체의 NET_VER 메모.
- NET_VER는 Area 버전의 `sanity_version_id`로 공통 카탈로그에서 찾는다. 카탈로그와 연결되지 않은 과거 버전이 계보에 있으면 그 구간은 "메모 적용 불가"로 표시하고 분석은 계속한다. 이름·정렬로 추측하지 않는다.
- OA가 분석 요청 시점에 적용 메모 목록을 확정해 실행 기록에 고정한다. 화면은 실행 전에 "이 분석에 쓰일 메모 N건"을 보여 준다.

### 5.3 후보 선별 (코드)

비교의 대응 그룹(instance)마다 누적 값으로 판단한다. 기준 숫자는 실행할 때 화면에서 바꿀 수 있고 실행 기록에 남는다.

| 후보 사유 | 조건 | 기본값 |
|---|---|---|
| Area 증가 | 양쪽 값이 있고 5.3a에서 빠지지 않음, Area Δ% ≥ 기준 | **+10% (임시값, [제안])** |
| Power 증가 | 양쪽 값이 있고 5.3a에서 빠지지 않음, Power Δ% ≥ 기준 | **+10% (임시값, [제안])** |
| 신규 instance | 기준 쪽 대응 없음 | — |
| 주요 instance | 등록 목록에 있음 | 항상 |

- 주요 instance를 제외한 후보는 현재·기준 중 큰 쪽 area가 **Area 최소(기본 50)** 이상이어야 한다. 화면의 Area 임계값과 같은 개념이다.
- 1단계는 증가만 본다.
- **조상 묶기:** 부모 값에는 자식 값이 들어 있어 자식 하나가 늘면 조상이 줄줄이 잡힌다. 어떤 후보의 증가분 중 **후보인 자식들의 증가분 합이 80% 이상**이면 그 후보는 독립 항목에서 빼고 자식 항목의 "영향받은 상위"로 기록한다. Area와 Power를 따로 판단하고, 한 지표라도 남으면 그 지표로 후보를 유지한다. [제안]
- **신규 묶기:** 신규 instance의 하위는 모두 신규이므로 가장 위의 신규 instance 하나만 후보로 둔다. [제안]
- 후보 사유는 **지표별로** 판단한다. Area는 비교되는데 Power는 안 되는 instance는 Area 사유만으로 후보가 될 수 있고, instance 전체를 비교 불가로 빼지 않는다. [제안]
- **주요 instance** [제안]
  - 묶지 않고, 기준 미만이어도 항상 AI에 보낸다. 상한과 호출 수에 포함된다.
  - 주요 instance는 증가·감소 양쪽을 본다(변화의 절댓값이 기준 이상이면 "눈에 띄는 변화").
  - 현재 쪽에는 있는데 기준 쪽 대응이 없으면 신규 instance로 AI가 판정한다.
  - 등록한 경로가 현재 실행에 없으면 AI를 부르지 않고 `현재 실행에 없음`으로 표시한다.
- **상한:** 후보가 상한(기본 400, 호출 약 20회)을 넘으면 분석을 시작하지 않고 기준을 올리라고 안내한다. 일부만 분석하지 않는다. 실행 전에 후보 수와 예상 호출 수를 미리 보여 준다. [제안]

### 5.3a 비교 조건이 확인되지 않은 instance [사용자 승인]

수치 엔진은 업로드 metadata(design_stage, constraint_context, classification, library, area_unit, area_basis, 분석 조건)가 양쪽에 채워져 있고 같을 때만 `비교 가능`으로 본다. 이 칸들은 대부분 선택 입력이고 프로젝트가 다르면 값이 다를 수 있다. 그 경우 Area·Power는 `조건 차이`(Δ는 계산), Vth·Drive는 `불가`(Δ%p 미계산)가 되어, 그대로 쓰면 Power → Vth → Drive 진단에 쓸 숫자가 없다.

**표의 상태 표시와 기존 계산 규칙(`comparability`, `evaluate_metric`)은 바꾸지 않는다.** AI 분석 쪽에서만 다음과 같이 처리한다.

1. **Area·Power가 `조건 차이`:** 후보에 넣고 정상 판정한다. 결과·메일에 "조건 미확인" 표시를 붙인다. `확인 필요`로 고정하지 않는다.
2. **Power를 분석에서 빼는 경우:** 양쪽 실행의 corner(process·voltage·temp·pex)가 다르거나, 분석 조건이 양쪽 모두 채워져 있는데 서로 다를 때. 뺐다는 사실과 이유를 결과·메일에 적는다. Area 사유의 후보는 그대로 분석한다.
3. **Area를 분석에서 빼는 경우:** area_unit이 양쪽에 적혀 있는데 서로 다를 때. [제안]
4. **Vth·Drive:** 업로드 metadata의 library·classification 칸과 무관하게, 양쪽이 보고한 비율의 차이(Δ%p)를 분석 모듈이 직접 계산해 진단 자료에 넣는다. library가 같은지는 사용자가 알려 준 규칙으로 판단한다: **프로젝트마다 공정이 있고, 공정이 같고 corner가 같으면 같은 library다.** [사용자]
   - 같은 프로젝트끼리는 공정이 같다. 다른 프로젝트는 양쪽 프로젝트에 등록한 공정이 같아야 한다.
   - 같은 library: 표시 없음.
   - 공정이 등록되지 않음: "library 미확인" 표시.
   - 공정 또는 corner가 다름: "library 다름 · Vth/Drive 구성 차이는 참고용" 표시. AI에도 알리고, 이 경우 Vth·Drive 변화만으로 원인을 단정하지 않게 한다.
5. 대응이 없는 것(신규 instance 제외), 매핑 충돌 등 엔진이 값 자체를 만들지 못하는 `불가`는 후보가 아니다. 주요 instance라면 그 사유를 그대로 표시한다.

### 5.4 진단 자료 (코드가 instance마다 작성)

- 경로(현재·기준), 후보 사유, 주요 여부, 비교 가능성
- Area: 기준·현재·Δ·Δ% (total, logic, sram)
- Power: total의 기준·현재·Δ·Δ%, internal·switching·leakage 각각의 Δ
- Vth 구성: 값이 달라진 항목의 기준→현재, Δ%p (일반과 LLP 구분)
- Drive 구성: 값이 달라진 항목의 Δ%p
- logic cell 수 Δ, 묶인 상위 목록, 증가분이 큰 자식 상위 3개

Area·Power 수치는 기존 계산(`evaluate_metric`)을 그대로 쓴다. Vth·Drive의 Δ%p만 5.3a의 4번에 따라 분석 모듈이 양쪽 보고 비율에서 직접 계산한다(logic area가 0이거나 비율이 비어 있으면 계산하지 않는다).

### 5.5 AI 판정

- 진단 자료 **20개씩 한 묶음** + 적용 메모 전체를 한 번에 보낸다. 입력 한도를 넘으면 묶음을 반으로 줄이고, 1개로도 넘으면 그 instance는 `확인 필요(입력 한도)`.
- AI는 사용자의 검토 순서대로 판단한다: ① 메모가 이 증가를 설명하는가 ② Power 증가가 Vth 변화로 설명되는가 ③ Drive 변화로 설명되는가 ④ 아니면 원인 불명.
- instance마다 돌려주는 것: 판정, 원인 분류, 짧은 설명(한국어), 근거로 삼은 메모와 인용 문장.

| 판정 | 뜻 |
|---|---|
| `설명됨` (expected) | 적용 메모가 이 변화를 설명함 |
| `이상` (unexpected) | 메모로 설명되지 않음. 원인이 Vth·Drive 변화로 보여도 **그 변화가 메모에 없으면 이상** |
| `확인 필요` (needs_review) | 메모가 방향만 말하고 규모는 설명 못 함, AI 실패 등 |
| `변화 미미` | **주요 instance 전용.** 기준 미만이고 눈에 띄는 구성 변화도 없음. 메모 인용이 필요 없다 |

신규 instance는 비교할 기준 값이 없지만 `확인 필요`로 고정하지 않는다. 메모가 그 instance의 추가를 설명하면 `설명됨`, 아니면 `이상`이다. [제안]

원인 분류: `메모`, `Vth 변화`, `Drive 변화`, `신규 instance`, `원인 불명`.

**코드가 하는 검증** (판정을 낮추는 방향으로만 고친다)

- 돌려준 instance 집합이 보낸 묶음과 정확히 같아야 한다. 다르면 그 묶음은 실패이고 해당 instance는 `확인 필요(AI 응답 오류)`.
- 인용한 메모는 적용 메모 목록에 있어야 하고, 인용 문장은 그 메모 본문에 실제로 있어야 한다.
- `설명됨`에는 유효한 메모 인용이 하나 이상 있어야 한다. 인용이 아예 없으면 `이상`으로, 인용은 했지만 유효한 것이 없으면 `확인 필요`로 내린다.
- `변화 미미`는 기준 미만인 주요 instance에만 허용한다. 기준 이상인데 `변화 미미`가 오면 `확인 필요`로 내린다.
- AI 출력에는 수치 필드가 없다.
- 관리자가 프로젝트 비교 AI 모델과 함께 묶음별 자동 재시도 한도를 지정한다(0~5회, 기본 5회). 실패가 확인된 일시적 모델 오류나 완전히 수신한 잘못된 판정에 적용한다. 한도를 소진한 항목은 확인 필요로 남기고 다음 묶음을 처리한다.

### 5.6 결과 화면

```
[AI 분석 ▸ Area +10% · Power +10% · Area 최소 50]   후보 132개 · 예상 호출 7회 · 적용 메모 3건
────────────────────────────────────────────────────────────────────────
이상 12 · 확인 필요 5 · 설명됨 31 · 주요 instance 8        [메일 보내기]

이상
  u_core/u_alu      Power +38% (Area +2%)
     원인: Vth 변화 · LVT 20% → 35% (+15%p) · 메모에 없음
  u_dma/u_buf       Area +65%
     원인: 메모 · "u_dma 버퍼 확장, 20~30% 증가 예상" 범위를 벗어남
확인 필요 …
주요 instance (항상 표시) …
설명됨 (접힘) …
```

- 항목을 누르면 Hierarchy Browser에서 그 instance까지 펼쳐 선택한다. 트리 행에도 판정 표시를 붙인다.
- 실행 중에는 진행(처리 묶음 수)을 보여 주고, 끝나면 자동으로 갱신한다.
- 지난 분석 실행도 다시 열 수 있다.

### 5.7 메일

- "메일 보내기"에서 수신자를 넣고(기본값은 설정된 기본 수신자), 뺄 항목을 고른 뒤 보낸다. 기본으로 `이상`·`확인 필요`·주요 instance가 들어가고 `설명됨`은 건수만 들어간다. [제안]
- 분석 1회에 메일 1통. 내용: 비교 대상(프로젝트·Block·NET_VER·REVISION·corner), 기준 숫자, 적용 메모 수, 판정별 목록(instance, Area/Power 변화, 원인, 설명), 실패·분석 제외 사실.
- 실패가 남은 분석은 메일에 그 사실을 적는다. 발송 이력(누가, 언제, 수신자, 뺀 항목)을 남긴다.

### 5.8 같은 프로젝트의 이전 버전 비교

- 비교 화면에서 비교 대상을 고른다: `기준 프로젝트와 비교` / `같은 프로젝트의 이전 버전과 비교`.
- 이전 버전 비교는 엔진의 기존 `previous_version` 종류를 쓴다. 기준 버전은 현재 버전의 명시적 계보에 있어야 한다(기존 검증).
- 같은 프로젝트이므로 같은 경로끼리 대응한다(기존 동작).

## 6. 저장과 API (기존 구조 위에서)

| 대상 | 저장 |
|---|---|
| 분석 실행 | `ai_run` 레코드. payload에 엔진 표시(`instance-triage-v1`), 기준 숫자, 고정한 메모·주요 instance, AI 연결 고정값, 처리 범위(후보 수·처리 수·실패 수) |
| 실행 작업 | `judge` job (중앙 VWP 소비). 부모 `ai_run`의 엔진 표시로 새 엔진에 분기 |
| instance별 결과 | `judgement` 레코드 (부모 = 실행, 실행+instance로 중복 방지). 진단 자료·판정·원인·설명·인용·묶인 상위 |
| 메일 | `mail` job (OA 소비). 부모가 분석 실행의 발송 기록이면 요약 메일로 분기 |

API는 기존 인증·프로젝트 권한을 따른다. 분석 실행과 메일 발송은 쓰기 권한이 필요하고, 조회는 로그인한 사용자 모두 가능하다.

- 메모·주요 instance 저장: 기존 `POST /config`, 조회는 기존 `GET /records`
- 실행 전 미리보기(후보 수·예상 호출 수·적용 메모·주요 instance 대응 상태)
- 분석 실행 요청
- 분석 결과 조회(실행 목록, instance별 결과 페이지)
- 요약 메일 발송 요청
- 실패분 재실행: 기존 `POST /jobs/{id}/rerun`

기존 `POST /comparisons/{id}/rejudge`와 기존 엔진의 동작은 바꾸지 않는다.

## 7. 구현자에게 맡기는 것

- 새 엔진 모듈의 파일 배치, 라우트 경로·이름, 응답 형태
- `change`/`target` payload 검증 모델의 확장 방식과 revision 처리
- 프롬프트 문구와 출력 스키마의 정확한 필드명
- 진단 자료의 숫자 자릿수, 묶음 크기(기본 20)·상한(기본 400)·조상 묶기 비율(80%)의 상수 위치
- 중앙 VWP에서 비교 뷰를 만드는 방식(기존 `observation_view` 캐시 재사용)
- 화면의 세부 배치, 트리에서 instance로 이동할 때 조상 경로를 받는 방법
- 요약 메일의 정확한 문구와 발송 기록 레코드의 모양
- 데모 모드의 합성 결과(AI 미호출 표시)

## 8. 확인 방법

- 후보 선별·조상 묶기·메모 적용 범위·응답 검증은 실제 코드를 메모리에서 실행해 확인한다(모델은 호출하지 않고 응답을 직접 넣는다).
- 백엔드 quick, tsc/production build, 합성 데모의 데스크톱 두 해상도 확인.
- 새 테스트 파일은 사용자가 승인할 때만 추가한다.
- 사내 모델의 판단 품질·실제 메일 발송·대용량 응답 시간은 사내 담당이 확인한다. 인계문에 확인 항목으로 적는다.

## 9. 나중 단계 (참고)

자동화는 "업로드되면 어떤 비교를, 누구의 AI 연결로, 누구에게"를 미리 등록하는 기능과 업로드 시 시작 조건을 더하는 것이다. 엔진·결과·메일은 그대로 쓴다. 수치 범위의 코드 대조, 감소 방향, 오탐 표시의 재활용도 이 뒤에 검토한다.
