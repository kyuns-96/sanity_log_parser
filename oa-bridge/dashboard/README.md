# OA 검토 대시보드

React·TypeScript·Vite·Tailwind CSS와 공식 shadcn/ui 구성 요소를 사용하는 한국어 검토
화면입니다. 외부 폰트·CDN·분석 서비스 호출 없이 로컬 자산과 시스템 폰트를 사용합니다.
서버 API와 같은 출처에서 제공하며, 접근 토큰은 탭 메모리에만 보관합니다.

프로젝트·담당자·블록별 버전·PoR의 업무 규칙과 운영 구현안은
[요구사항 15절](../../requirement.md#dashboard-domain-spec)을 따릅니다. 아래는 현재 데모의 사용법과 구현 범위입니다.

```sh
cd oa-bridge/dashboard
npm ci
npm run build
```

`dist/`를 OA 서버가 제공합니다. 서버 실행과 접근 토큰 발급은 상위 OA 문서를 참고합니다.
프런트엔드에 서버 토큰, DB 비밀번호나 연결 문자열을 넣지 않습니다. 브라우저 저장소나
URL에 인증 토큰을 기록하지 않으며 새로고침 후 다시 로그인해야 합니다.

개발 시 `npm run dev`는 `127.0.0.1:5173`에서만 수신하고 `/api`를 로컬
`127.0.0.1:8000`으로 전달합니다. 사내망 배포 시 의존성을 사전에 준비하고
`npm ci`와 빌드를 실행할 수 있는 오프라인 환경을 구성해야 합니다.

로그인 화면의 **데모 둘러보기** 또는 명시적인 `?demo=1`에서만 데모 데이터를 확인할 수 있습니다.
데모에서는 API를 호출하지 않으며 변경 내용을 현재 탭 메모리에만 저장합니다.
API 장애·인증 실패 시 오류를 표시하고 자동으로 데모로 바꾸지 않습니다.

프로젝트·담당자 배정 흐름은 `/?demo=1&flow=access`에서 체험합니다. 상단의 가상 계정을
전환하면 관리자, 프로젝트 TOP, 블록 담당자, 미배정 사용자의 화면을 비교할 수 있습니다.
관리자의 **프로젝트 만들기**에서 기본 정보·TOP → 블록·담당자·검사 목록 → 확인의 3단계를
진행합니다. 등록한 검사는 모두 미수신 상태로 시작합니다. **담당자 설정**에서 배정을
추가·해제하고 프로젝트 관리 권한을 별도로 지정하면 다른 계정의 화면에도 즉시 반영됩니다.
TOP의 조회 범위와 관리 권한, 글로벌 프로젝트 생성 권한은 구분합니다. 변경 이력도 제공합니다.
이 데모는 브라우저 메모리에서만 동작하며 SSO·DB·실제 서버 권한 검증을 구현하지 않습니다.
새로고침하거나 **초기화**를 누르면 처음 상태로 돌아갑니다. `flow=access`만으로는 열리지 않습니다.

블록별 PoR·ECO 버전 조회는 `/?demo=1&flow=versions`에서 체험합니다.
**NET_VER·REVISION은 프로젝트 안의 각 블록에 속하며, 블록 담당자가 한 조합을 해당 블록의 PoR로 지정합니다.**
상단에는 블록별 담당자와 현재 PoR의 NET_VER·REVISION을 표시합니다. CPU·GPU·DDR의 버전 목록,
현재 PoR, ECO, 검사 결과는 각각 독립적입니다. 프로젝트 전체를 대표하는 공통 PoR 번호는 없습니다.
블록 → PRE/POST → NET_VER·REVISION → ECO → sanity 결과 순서로 조회합니다.

데모 사용자에서 **이영희 · Atlas TOP**은 모든 블록을 조회합니다. **김철수 · CPU 담당자**는
CPU를, **박민지 · GPU·DDR 담당자**는 GPU·DDR을 조회하고 각 담당 블록의 PoR을 지정합니다.
담당 블록에서 버전을 조회한 뒤 **CPU PoR로 지정** 같은 버튼으로 지정합니다.
단순한 버전·layout·ECO 조회는 PoR을 변경하지 않습니다. 지정은 해당 블록의 NET_VER·REVISION만
참조하며 다른 블록의 PoR, ECO, 기존 검사 결과를 변경하지 않습니다.
계정과 배정은 담당자 데모의 초기 예시를 재사용하며, 두 화면의 변경 상태를 공유하지는 않습니다.
이 권한 동작은 브라우저 데모이며 운영 SSO·서버 권한 검증은 아닙니다.

CPU NET_VER 예시는 `EVT0_ML3_DEV00 → EVT0_ML3_DEV01 → EVT0_ML4_DEV00`입니다.
GPU는 `EVT0_ML2_DEV01 → EVT0_ML3_DEV00`, DDR은 `EVT0_ML1_DEV00 → EVT0_ML2_DEV00`으로
블록별 진행 차이를 보여줍니다. CPU PRE revision `M4D0S1-hakhyun-Wsaif-v00-Cktran`의
POST revision은 `M4D0S1-hakhyun-Wsaif-v00-Cktran_beaifs-m5ps-BE`입니다.
전체 이름을 그대로 표시하며, PRE와 POST는 블록 내부에서 연결된 별도 세트로 보관합니다.
초기 PoR은 POST 조합이며 담당자는 PRE 또는 POST의 정확한 NET_VER·REVISION 조합을 지정할 수 있습니다.
이는 블록당 현재 PoR 하나를 두는 데모 동작이며, PRE·POST별 PoR 운영 정책의 최종 확정과 구분합니다.

POST 최초 ECO는 `chip_finish`이며 이후 예시는 `eco01 → eco02 → …`입니다.
같은 `eco01`이어도 프로젝트·블록·NET_VER·REVISION이 다르면 검사 결과와 실행 이력이 분리됩니다.
CPU의 `EVT0_ML4_DEV00` POST eco03은 결과 미수신 예시입니다.
운영 검사 결과의 원천은 VWP에서 전송한 데이터입니다. 대시보드는 수신 결과를 조회·검토하며,
검사 실행이나 PASS/FAIL을 생성·편집하지 않습니다. 이 데모는 미리 준비된 예시를 사용합니다.
PoR 지정과 검토는 브라우저 메모리에만 저장되며 새로고침·초기화 시 돌아갑니다.
실제 VWP·EDA·SSO·DB 호출이나 운영 데이터 변경은 없습니다.

GCA 예시는 `/?demo=1&dataset=gca` 또는 데모 배너의 **GCA 예시 보기**에서 엽니다.
Atlas/Boreal 두 가상 프로젝트, 프로젝트별 CPU/GPU/DDR 네 블록, 다섯 실행의
`CLK_0003`, `CAS_0003`, `CLK_0026`, `EXD_0012`, `B2T_CAS_0001` 사례를 제공합니다.
프로젝트·블록을 선택한 뒤 실행과 sanity item을 고르면 예시 보고서 전체·출처·`.rpt`
다운로드를 확인할 수 있습니다. 같은 이름의 블록도 프로젝트와 실행별 검토 이력을 분리합니다.
PASS와 report 미도착 상황을 포함하며 AI 분류는 실제 호출하지 않습니다.

자료는 [Synopsys GCA 백서](https://www.synopsys.com/content/dam/synopsys/implementation%26signoff/white-papers/GCA_wp.pdf)
(2010, pp. 2, 6–8)와 [PrimeTime GCA User Guide 공개 열람본](https://www.scribd.com/document/807828202/PrimeTime-GCA-User-Guide-2016)
(Synopsys, L-2016.06, Chapter 2 / Example 2-8 / Appendix A)을 참고했습니다.
문서의 검사 의미와 규칙 번호를 참고하되 객체·수치·판정·보고서 문구는 데모용으로 구성한 예시 데이터입니다.
vendor report 전체나 이미지를 복제하지 않았으며, native report 형식·현행 버전의 규칙 호환·
실제 파서·DB·AI 연동 검증 자료로 사용하지 않습니다. 규칙별 묶음은 동일 원인 확정이 아닙니다.
프로젝트·블록 선택은 이 데모의 예시 탐색 기능이며 운영 API의 범위 관리 구현을 뜻하지 않습니다.

화면에서 접수 목록과 실행을 선택하고, 전체 점검 대장·문제 그룹·원문 예시·생략 수를
확인할 수 있습니다. 사람의 판단은 현재 개정과 요청 UUID를 함께 제출합니다.
실패한 명령을 그대로 재시도하면 같은 UUID를 유지하고, 내용을 수정하면 새 UUID를
생성합니다. 개정 충돌 시 검토 창을 닫고 새로고침한 후 다시 검토해야 합니다.
FAIL을 PASS로 바꾸는 입력과 분석 미완료 항목의 검토는 비활성화하며 서버에서도 검증합니다.

추가 근거는 알려진 기록 ID를 직접 입력할 수 있으며 PASS 항목에서도 요청할 수 있습니다.
VWP 요청 처리 상태와 OA 응답 수신 상태를 따로 보여줍니다. OA에서 응답을 검증하여
`RECEIVED`로 처리한 뒤에만 근거 본문을 열 수 있습니다. 근거 수신은 사람의 승인과 별개입니다.
이력은 API가 반환하는 최근 50개 범위와 전체 개수를 표시하며 전체 기록은 서버에 보존됩니다.
검색과 필터는 현재 점검 대장 페이지에만 적용합니다.

브라우저 검증:

```sh
npx playwright install --with-deps chromium
npm run test:e2e
```

Playwright는 실제 Chromium에서 명시적 데모, 로그인과 토큰 비저장, API 실패,
UUID 재시도·개정 충돌, 읽기 전용, 판단 기록, 근거 요청·응답, 보고서 다운로드,
390px 모바일 화면을 확인합니다. 데모 및 API 모킹 기반 UI 테스트이며 실제 DB·API 통합
검증은 상위 프로젝트 테스트와 별도로 수행합니다. 화면 캡처는 `artifacts/`,
결과 보고서는 `playwright-report/`에 생성됩니다.
