# Codex 답변 — VWP Q1 수집·인계 설계

기준: 2026-10-16. 사용자 요청으로 설계를 검토·보완했다. 상세 기준은 [분산 수집·PRE/POST 설계](../../vwp/SOURCE_COLLECTION_DESIGN.md), 현재 실행 계약은 [PLAN_INTEGRATION.md](../../vwp/PLAN_INTEGRATION.md), 작업 허용 범위는 [INTERNAL_AI_GUIDE.md](../../INTERNAL_AI_GUIDE.md)다. 문의 원문 Q1은 수정하지 않는다.

후속 사용자 요청으로 [제출 실행 안내](../../vwp/SUBMISSION.md)의 CLI·접수/영속 보관·V2 분할 전달·OA 원자 반영/receipt를 구현했다. 실제 회사 원천/신원·승인 SDK·인증된 mount/ACL·운영 DB는 미연결이다. 가이드에 허용된 `corporate_submission.py` 메서드와 회사 wrapper만 연결하며 공통 CLI/작업자·DB를 재구현하지 않는다.

## Q1. PRE/POST의 여러 물리 루트 export

허용한다. 자기 `vwp/integration/company_plan/` launcher에서 VWP 내부의 별도 report 입력 root에 **원본과 byte 동일한 일반 파일 사본**을 준비한 뒤 기존 collector를 호출한다. `get_plan()`은 plan만 반환하고 복사/파일 쓰기는 하지 않는다.

`collect --reports`에 넘기는 root 아래 `pre/<mode>/<item>/...`, `post/<slot>/<mode>/<item>/...`를 두면 plan의 report는 `reports/pre/...`, `reports/post/...`다. 원본 완료·복사 전후 원본/사본 hash·안전 경로를 검사하고 원본은 바꾸지 않는다. 누락 unit을 삭제하거나 예상 밖 report를 숨기지 않는다. plan/완료 표식/승인 자료는 report root 밖에 둔다. OA로 파일을 직접 전달하지 않는다.

## Q2. stage와 design

GCA 수집 프로필의 공통 업무 stage는 `sanity`로 정의한다. 이는 수집 업무의 표준 매핑이며 실제 회사 물리 단계가 확인됐다는 뜻이 아니다. mode는 unit 조건에 두고 PRE/POST·ECO·REVISION을 stage에 합치지 않는다. design은 확인된 설계/블록 식별자이며 NET_VER로 대체하지 않는다.

PRE/POST의 실제 tool/version과 물리 source stage는 각각 보존한다. 기존 schema 1은 한 tool/version만 표현하므로 다른 버전을 한 값으로 덮지 않는다. 새 제출은 별도 V2의 source별 메타데이터를 사용한다.

## Q3. NET_VER·REVISION·ECO·PRE/POST

V2는 제출 묶음의 `collection`과 개별 report의 `inventory.units[].source`로 명시적으로 분리한다. PRE report는 자기 PRE 버전에 속하고 POST 제출에 들어갔다고 POST report가 되지 않는다. PRE의 업무 ECO는 null이며 물리 슬롯 이름 `pre`와 다르다.

실제 대응표를 확인해 허용된 `CorporateSubmissionInput.prepare`에서 고정 V2 plan과 원본 Path를 반환한다. 기존 CollectionPlan/schema 1을 변경하거나 condition에 버전 정보를 끼워 넣지 않는다. condition은 legacy 재사용 범위에 포함되므로 REVISION 운반용으로 쓰면 버전마다 범위가 갈라진다. source import·검증/저장은 제공된 공통 작업자를 사용한다.

## Q4. scan 기반 예상 목록과 confirmed=false

중앙 마스터 목록이 없어도 담당자가 명시적으로 승인한 **예상 범위 선언서**를 원천으로 사용할 수 있도록 설계를 보완했다. 디렉터리는 슬롯 후보만 찾고, 선언된 슬롯×mode×item 및 PRE 관계로 예상 집합을 생성한다. 실제 report 존재 수로 예상 수를 정하지 않는다. POST 슬롯 두 개+PRE, mode 세 개, item 하나면 기대 단위는 9개이며 파일이 8개라면 누락 1개를 유지한다.

승인은 정확한 예상 집합 digest·프로필 개정·범위에 결합하고 실제 주체와 블록 권한·시각·근거를 확인한다. PC 사용자명·REVISION 안의 이름·입력 approved_by만으로 승인하지 않는다. 승인 원천이 없으면 `confirmed=false`를 유지한다. V2 공통 코드가 digest와 회사 `approval_valid` 결과를 대조하며 실제 승인/담당 SDK는 사내 구현이 필요하다. 기존 판정 저장/전체 완료 차단을 우회하지 않는다.

이 범위 승인이 evaluation 임계값·단위·업무상 적용 제외 승인을 대신하지 않는다. 미확정 기준은 추정하지 않는다.

## Q5. 분산 수집 ID와 중복

기존 bridge는 입력 계약 기반 analysis_id, OA legacy는 bundle_id로 같은 분석의 재수신을 식별한다. 새 V2는 별도 원천 키·staging/원자 import로 workspace에 연결한다.

목표 설계는 `source namespace + project + block + NET_VER + 전체 REVISION + PRE/POST`의 버전 키, ECO/item/mode의 단위 키, 실제 원천 실행 키, raw bytes snapshot 키, parser/규칙에 따른 분석 개정, 제출 내용 ID와 요청 UUID를 분리한다. 서로 다른 POST가 포함한 동일 PRE 실행은 한 원본을 참조한다. 같은 실행의 다른 원문은 충돌로 보류하고, 실제 재검사는 새 execution_ref로 보존한다.

**추가 인계가 필요한 사실은 execution_ref와 실행 순서의 원천/안정성이다.** 다른 PC에서 같은 실행을 재전달할 때도 같은 참조를 보존해야 한다. 임의 PC별 UUID·복사 시각·mtime·파일 내용 해시만으로 같은 바이트 재검사를 구별할 수 있다고 가정하지 않는다. 현재 project/net_ver/revision 조합만으로 전체 중복 정책이 완성된 것으로 보고하지 않는다.

## 작업 재개 범위와 남은 사실

허용된 회사 입력/신원·권한·승인 메서드와 wrapper·원천 대응표·전용 테스트는 가이드 범위에서 준비한다. 공통 코드·SQL·기존 테스트·schema/worker/API/UI는 수정하지 않는다. V2는 새 제출 CLI/source 작업자를 사용하며 기존 collect/analyze에 투입하지 않는다.

확인할 사실은 project/block 안정 키, PRE 단독/POST REVISION 문법의 적용 범위, ECO 자리수/alias, mode·capture 범위의 실제 승인, 완료 표식의 실행 연결, PRE/POST tool/version, execution_ref·실행 순서, 예상 목록 승인 경로, 임계값/제외 승인 근거다. 사실이 없으면 `FACTS_REQUIRED`, 예상 밖 오류/테스트 실패는 `WAITING_FOR_CODEX`로 남긴다. 원문/비밀은 사내에만 보관하고 Codex에는 합성 구조와 비식별 결과만 전달한다.
