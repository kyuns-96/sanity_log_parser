# 같은 AI 작업 안의 병렬 배치 호출

관리자 AI 연결 화면의 **처리 한도와 전체 로그 배치 설정 → 작업당 동시 호출 수**에서 1~8을 설정한다. 기본은 1(기존 직렬 실행)이며, 사내 모델의 허용 동시성을 확인하고 2부터 측정한다. 배치를 켠 **새 작업**에 적용한다. 단일 호출은 분할하거나 복제하지 않는다.

연결 JSON의 선택 설정은 `batch.max_concurrency`다. 예를 들어 기존 batch 설정에 `"max_concurrency": 2`를 추가한다. 기존 설정을 읽거나 저장하는 것만으로 이 키를 추가하지 않는다. 기본값 1은 기존 공개 설정과 config pin에 영향을 주지 않는다. legacy 환경 설정은 `SANITY_OA_AI_BATCH_MAX_CONCURRENCY=2`를 지원한다.

## 실행과 이력

- 한 단계에서 최대 설정 개수의 배치를 독립 예약하고 HTTP 호출을 동시에 실행한다. 각 요청의 실행 위치 ContextVar와 모델 객체를 분리하며 DB 연결/트랜잭션/권한 잠금을 HTTP 스레드와 공유하지 않는다.
- 응답이 오는 순서대로 별도 짧은 트랜잭션에서 검증·저장한다. 같은 단계의 모든 배치 결과가 모이기 전에는 다음 통합 단계로 가지 않는다. 원본 순서는 계획의 index로 복원하며 부분 결과를 최종 제안으로 공개하지 않는다.
- 작업별 예약으로 여러 worker가 같은 배치를 중복 실행하지 않도록 한다. 이 수치는 **한 작업에서 추적 중인 요청 수**의 상한이며 여러 작업/프로세스의 전체 API 호출 수나 원격에서 끝나지 않은 요청의 전역 상한은 아니다.
- 새 부모 작업에 `batch.execution=parallel-v1`과 동시 호출 수를 고정한다. 기존 `batch.version=1/2`는 분류/본문·그룹 판정의 내용 계약으로 유지한다. 기존 작업을 병렬 이력으로 바꾸지 않는다.
- 기존 네 테이블의 불변 예약·응답·단계 이력을 사용한다. 새 DDL/GRANT나 별도 큐 서비스는 필요하지 않다. 전체 원본·배정·인용·기준/사례·개인 인증·현재 권한과 입력 개정 검증은 유지한다. [item별 입력 선택](AI_INPUT_FIELDS.md)과 함께 사용할 수 있다.

## 실패·중단·복구

안전하게 실패한 호출은 기존 정책대로 최초 시도 이후 최대 5회 재시도한다. 같은 묶음의 성공한 배치는 다시 호출하지 않는다. 실패·불명·진행 중 예약을 포함한 시도 수로 전체 호출 예산을 지킨다. 429와 backoff가 길면 그 묶음의 남은 처리가 지연될 수 있다.

읽기/쓰기 timeout이나 예약 후 프로세스 종료로 알 수 없는 결과는 자동 재전송하지 않는다. 이미 예약한 다른 호출이 끝나거나 기한에 도달할 때까지 결과를 수집한다. 프로세스 재시작도 기존 예약을 재전송하지 않으며 만료된 요청만 UNKNOWN으로 기록한다. DB에 commit한 성공 결과를 보존한다. 원격 응답 직후 DB 저장 전에 프로세스가 종료된 호출은 결과 불명이 될 수 있다.

모든 진행 중 호출을 확인한 뒤 원래 요청자가 **화면에 표시된 미확인 배치 목록 전체**의 중복 가능성을 한 번 확인해 재시도할 수 있다. 요청 UUID와 부모/목록 checkpoint hash로 정확한 집합을 고정한다. 이미 완료한 형제 배치는 재사용하고 늦은 이전 응답은 새 예약을 덮어쓰지 못한다. 안전하게 재개할 수 없는 영구 실패가 섞이면 복구를 차단한다. 일반 재개와 같은 최대 5회 및 전체 호출 예산을 공유한다.

취소는 새 전송을 막고 `취소 요청됨`으로 표시한 뒤 진행 중 응답을 확인한다. 알려진 결과는 저장하되 최종 제안을 반영하지 않는다. 모든 호출이 확인되면 CANCELLED, 미확인 호출이 남으면 UNKNOWN이다. 안전한 취소의 명시 재개는 이미 끝난 배치를 보존한다. 원격 API 요청 자체를 중단하는 기능은 아니다.

## 현황과 배포

카드는 현재 동시 호출 수와 전체 단계의 완료 수를 표시한다. 병렬 HTTP 소요 시간의 합을 실제 경과 시간으로 사용하지 않는다. 단계의 첫 실제 예약부터 마지막 성공 저장까지의 경과 시간과 완료 로그 수로 **최근 분류·판정 건당 평균**을 계산한다. 성공 호출 표본이 두 개 이상 모인 뒤부터 표시하며, 본문·통합 단계에서는 마지막 유효한 로그 검토 평균을 유지한다.

**이번 단계 예상 종료**는 같은 표본의 로그 처리율 또는 본문·통합 배치 처리율과 남은 작업량으로 계산한다. 표본의 실제 완료 시각을 기준으로 하므로 상태 조회만으로 예상 시각이 뒤로 밀리지 않는다. 이후 통합·최종 검증을 포함한 전체 작업 완료 예상은 아니다. 표본 부족·재시도 대기·취소·실패/결과 불명·종료 상태에서는 ETA를 표시하지 않는다. 단계와 재개 회차가 바뀌면 새로 측정하며, 측정 정보가 없는 기존 작업은 다음 예약부터 표본을 모은다. 단일 호출/기존 직렬 작업의 측정은 유지한다.

OA 웹과 중앙 VWP 작업자를 같은 지원 릴리스로 맞춘 뒤 새 작업에 활성화한다. 기존 연결의 설정 개정을 바꾸면 진행 중 작업이 STALE이 될 수 있으므로 먼저 현재 작업 상태를 확인한다. 기존 형식 작업은 직렬로 계속 읽는다. 실제 사내 API의 동시 허용 수, 429 비율, 입력 준비·DB 검증 시간과 모델 응답 시간을 함께 측정한다. 병렬화가 설정 배수만큼 빨라진다는 보장은 없다.

내부 AI의 기존 회사 어댑터 허용 범위와 오류 시 `WAITING_FOR_CODEX` 규칙은 확대하지 않는다. 공통 병렬 엔진·저장·UI·테스트 수정은 설계 담당 Codex가 맡는다.
