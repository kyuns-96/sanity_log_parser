# 제출 실행 이력·보고서 삭제·rule code 그룹

2026-11-02 사용자 결정. 같은 revision을 반복 제출할 때 revision 문자열을 바꿀 필요가 없다. 원천 버전은 하나로 유지하고 **새 제출 UUID마다 별도 보고서 실행**을 보존한다. 같은 UUID의 전송 재시도는 같은 실행이며 새 보고서를 만들지 않는다. 파서·수집 수정 후 재제출은 새 `sanity submit`을 사용한다.

## 제출과 최신 표시

새 실행 ID는 기존 원천 단위·실행 사실에 제출 UUID를 결합한다. `source.execution_ref`와 `execution_order`의 실제 원천 값은 그대로 보존하며 임의로 증가시키지 않는다. `SOURCE_RUN.unit_key`는 제출 실행 안에서 유일하고 `source_unit_key`는 원래 안정 단위다. 분석 원본도 제출별로 분리되므로 수정된 원문이 이전 보고서나 사람 확정 이력을 덮어쓰지 않는다.

bridge는 private `SUBMISSION.created_at`을 UTC `submitted_at`으로 모든 패킷과 보고서에 고정한다. OA는 제출 UUID와 시간의 결합을 검증한다. 원래 단위별 최신 목록은 제출 시각을 우선하고 구형 보고서는 기존 실행 순서로 정렬한다. 화면 이름은 `item · 제출 일시`이며 상세의 실제 report ID는 유지한다. **제출 이력 포함**으로 과거 실행도 확인한다. 전송 도착 순서를 실제 원천 실행 시각으로 해석하지 않는다.

업그레이드 전에 일부 outbox를 만든 제출은 `legacy` 모드로 재개한다. 새 모드 결정은 첫 패킷 생성 전에 저장하고 파싱 재개에도 유지한다. 기존 패킷·원문·해시를 덮어쓰지 않는다. CLI·bridge·OA 수신기를 같은 릴리스로 배포한다.

## 버전·보고서의 물리 삭제

현재 블록 OWNER가 버전/보고서 목록의 삭제 버튼으로 범위를 조회한 뒤 확인한다. 삭제는 관련 **원본 DB 바이트, 파싱 로그, AI 작업/중간 결과/분류·판정, 사람 확정 이력**까지 포함한다. 다른 보고서가 함께 사용하는 조각·원본은 마지막 참조 삭제 시 정리한다. OS 파일 삭제나 외부 모델 요청 취소는 이 API의 범위가 아니다.

- `GET /api/workbench/blocks/{block}/versions/{version}[/reports/{report}]/delete-preview`
- `POST` 같은 경로의 `/delete`: `{request_id, snapshot_sha256}`. UUID와 미리 본 범위를 고정한다. 응답 유실 시 같은 요청으로 결과를 확인한다.
- 현재 PoR 또는 다른 POST의 PRE 기준인 버전은 먼저 연결을 정리해야 한다. 권한·원본·사람 확정 상태가 미리보기 이후 달라지면 다시 확인한다.
- **single_account와 기존 네 테이블의 SELECT/DELETE 권한**이 필요하다. 앱은 GRANT·DDL·설치 함수를 만들지 않는다. restricted의 DELETE 금지는 유지한다.
- 양쪽 DB 자료를 하나의 트랜잭션으로 정리하고 실패하면 모두 롤백한다. 처리 중인 제출/업로드 잠금이 있으면 `SUBMISSION_BUSY`로 거부한다.
- 삭제 제출은 최소 거부 표식만 남겨 늦은 패킷/receipt/AI 응답과 기존 UUID 재사용을 차단한다. 표식에는 삭제한 본문이나 사람 근거를 복사하지 않는다. 버전 삭제 후 새 제출 UUID·새 접수 시각으로 같은 원천 버전을 다시 만들 수 있다.

카드의 **AI 작업 삭제**는 실행 기록만 지우고 이미 적용한 분류·판정과 보고서 원본을 보존한다. 버전/보고서 삭제와 범위가 다르다. 원본·확정 근거까지 삭제하려면 버전/보고서 삭제를 사용한다.

## rule code가 첫 그룹 계층

모든 sanity의 실제 코드 필드는 파서의 `ParsedRecord.fields.code`다. **서로 다른 code는 의미가 비슷해도 같은 그룹에 넣을 수 없다.** 같은 code 안에서 조건·패턴에 따라 AI가 세부 그룹을 나눈다. 이름은 `RULE_CODE · 간단한 그룹 설명`이며 서버가 접두어를 정규화하고 code 순서로 저장한다. 기존 120자 한도 안에서 설명만 줄이며 code는 자르지 않는다. 제어 문자나 110자 초과 code는 명시 오류다.

AI 출력·최종 전체 배정·수동 이름 변경·병합·이동·새 그룹 저장에 같은 검사를 적용한다. leaf는 원본 순서를 유지하며 연속된 동일 code 안에서 나누고 중간 그룹 병합 후보도 code별로 제한한다. 완료 배치의 원본 index를 바꾸지 않는다. 과거 확정 이력은 읽기 시 고치지 않으며 혼합된 과거 그룹은 새 개정에서 분리한 뒤 저장해야 한다.

`ai_fields`에 code가 없어도 분류 요청의 `report.rule_codes`에 **요청별 ID → 실제 code**만 제공한다. 제외한 raw·다른 필드는 추가 전송하지 않는다. 이 구조 정보는 `grouping_policy=rule-code-v1` 및 요청 hash·프롬프트 버전에 기록한다. 전송형 `PARTS_V2`는 실제 code 누락을 item 이름으로 메우지 않는다. 옛 단일 규칙 workspace snapshot만 명시된 `report.rule`을 호환 값으로 사용한다.

기존 단일/저장 완료 결과도 새 게시 시 경계를 검사한다. code가 섞인 결과를 자동 분할해 근거를 만든 것으로 처리하지 않는다. 이미 성공한 leaf는 재개 시 유지하지만 새 경계에 어긋나는 과거 결과는 오류로 남을 수 있다. 회사 파서는 실제 code 대응을 확인하고 임의 code를 만들어 채우지 않는다. 내부 AI의 수정 허용 범위와 오류 시 중단 규칙은 그대로다.
